# 文案与多语言

CommandPark 的所有用户可见文案都在程序目录的 `lang\<语言标记>.json` 里，代码通过路径取值：

```csharp
Localization.Get("chat.title");                       // XAML 之外的地方
Localization.Format("search.aiBadge", "Ctrl");        // 带 {0} 占位符
```

```xml
<TextBlock Text="{loc:Loc search.searching.normal}"/>  <!-- XAML 标记扩展 -->
```

这份文档说明**键怎么摆**（分组、深度、命名）、**新增语言怎么做**，以及**单测怎么兜底**。

## 1. 语言文件与查找顺序

- 位置：`lang\<语言标记>.json`，语言标记用 `语言_地区`（`zh_CN`、`en_US`、`pt_BR`）。构建时按「如果较新则复制」进输出目录，AOT 发布包也会带上 `lang\`。
- 内容：一棵 `键 → 文案` 的 JSON 树，只允许字符串叶子（值里可以有 `{0}` 占位符）。
- 中文 `zh_CN.json` 是**基准**：所有语言文件必须与它键集合、占位符集合完全一致（单测会检查）。
- 查找顺序由 `commandpark.json` 的 `language` 节点决定：

  **当前语言 → `language.fallback`（按顺序） → `language.base`（默认 `zh_CN`）**

  例如 `current: "en-US"`、`fallback: ["ja_JP"]`、`base: "zh_CN"` 时，`en_US.json` 里缺的键会去 `ja_JP.json` 找，再缺就去 `zh_CN.json`。全都缺时把键路径原样显示出来，便于一眼发现漏翻译。
- 语言标记容错匹配：`en` / `en-US` / `en_US` 都能找到 `en_US.json`；`zh-Hans-CN` 会依次试 `zh_Hans_CN` → `zh_CN` → `zh`。
- 缺失或损坏的语言文件会被跳过，不会拦住启动。

### 新增一门语言

1. 复制 `lang/zh_CN.json` 为 `lang/<语言标记>.json`；
2. 只改「值」，不动「键」，键与占位符保持一一对应；
3. 想让它默认生效就设 `language.current`，或者让用户自己改；放在 `fallback` 列表里也可以作为回退语言。

不需要改任何代码，也不需要改 `csproj`（`lang/*.json` 是通配复制）。

## 2. 键的布局规则

### 2.1 同一领域的字符串放在同一个分组

一个功能、一个窗口、一个搜索源就是一个「领域」，它们的文案放在同一个对象里。这样找文案时只需要知道「哪个功能」，不用记长键名。

**应**（`sources.calc` 是「计算源」这个领域，`result` / `timeout` / `desmos` 是它产出的几种 Hint）：

```json
{
    "sources": {
        "calc": {
            "result": { "description": "高级计算器，按 Enter 查看详情", "action": "在 Desmos 中打开 (Alt+D)" },
            "timeout": { "name": "计算超时", "description": "表达式计算超过 {0} 秒，已取消。" }
        }
    }
}
```

**不应**：嵌套太深、每层只有一两个键。下面是 5 层、每层都只有一个子节点的反例：

```json
{
    "home": {
        "banner": {
            "messages": {
                "welcome": {
                    "out": "欢迎使用"
                }
            }
        }
    }
}
```

**不应**：无嵌套、单层平铺一大堆键，谁也看不出哪几个是一起的：

```json
{
    "welcome": "欢迎使用",
    "up": "上一个新闻",
    "down": "下一个新闻",
    "imageUp": "上一张",
    "imageDown": "下一张",
    "userName": "用户名",
    "userLevel": "用户等级"
}
```

### 2.2 按相邻用途分割，别把多个词压进一个键

同一个东西的一组成员（名称 / 描述 / 按钮文案 / 正文模板）应该拆成一个分组，而不是靠键名后缀区分。

判断口诀：**看单词数**。1 个词不用拆；2 个词可拆可不拆；3 个词以上就该拆。

| 键 | 单词数 | 结论 |
| --- | --- | --- |
| `user` | 1 | 不拆 |
| `userName` | 2 | 可拆 → `user.name`（有 `userLevel` 之类的兄弟时更该拆） |
| `userStatusOffline` | 3 | 必须拆 → `user.status.offline` |

**应**（`timeout` 这个 Hint 的名称与描述是相邻用途的一对）：

```json
{
    "timeout": {
        "name": "计算超时",
        "description": "表达式计算超过 {0} 秒，已取消。"
    }
}
```

**不应**（`timeoutName`、`timeoutDescription` 两个键共享前缀却各写一次）：

```json
{
    "timeoutName": "计算超时",
    "timeoutDescription": "表达式计算超过 {0} 秒，已取消。"
}
```

**应**（三个打开动作共用一个 `open` 分组）：

```json
{
    "open": {
        "file": "打开 {0}",
        "folder": "打开文件夹 {0}",
        "drive": "打开驱动器 {0}"
    }
}
```

### 2.3 层级与宽度

| 规则 | 限制 | 说明 |
| --- | --- | --- |
| 深度 | ≤ 4 层 | `sources.everything.unavailable.description` 这种「领域.来源.Hint.用途」是最深的情况 |
| 每段单词数 | ≤ 2 | 3 个词就拆成两级 |
| 单个分组键数 | ≤ 8 | 再多就继续分组，别让一层平铺 |
| 顶层分组数 | ≤ 12 | 顶层是「领域列表」 |

**不要**为了凑兄弟而造出多余的一层：只有 1 个字符串的领域（`common.listSeparator`、`config.invalidRoot`）就是单键分组，没必要为了对称再加一层。

### 2.4 命名风格

- 统一 `camelCase`，不用 `_` / `-`；语言标记里的 `_` 只有目录文件名用。
- 段落用**用途词**，而不是数字或 `text1`：`name`、`description`、`action`、`title`、`heading`、`input`、`output`、`badge`、`confirm`。
- Hint 的约定：一个 Hint 有名称和描述时，放 `<hint>.name` / `<hint>.description`；只有 1 个字符串时，直接把这个字符串放在 `<hint>` 上（例如 `sources.bing.suggestion`）；搜索源里只有 1 个 Hint 时，它的字段直接放在来源分组下（例如 `sources.run.name`）。
- 「正常 / AI 模式」这类成对的变体，用 `normal` / `ai` 两个子键，不要写 `xxxAi` / `xxxAiMode`。

## 3. 现有分组一览

| 分组 | 放什么 |
| --- | --- |
| `common` | 跨领域复用的小片段（如列表分隔符） |
| `config` | 读取/校验配置文件时的报错 |
| `background` | 启动阶段：后台程序拉起、全局热键提示 |
| `search` | 搜索主窗口：占位符、空闲/搜索中提示、空结果、AI 模式徽标 |
| `chat` | AI 聊天窗口：标题、角色名、按钮（`button.*`）、导出文件（`export.*`） |
| `error` | 命令执行失败窗口：标题、提升权限（`elevation.*`）、权限问题（`permission.*`）、各条人话说明 |
| `details` | Hint 详情窗口 |
| `ai` | AI 相关：`config.*` 配置报错、`prompt.*` 系统提示词、`tool.*` 工具描述、`session.*` 工具输出（`session.field.*` 是字段标签） |
| `sources` | 各搜索源产出的 Hint 名称与描述 |

`sources` 下的 7 个来源与它们在代码里的类一一对应：

| 分组 | 对应 | Hint 结构 |
| --- | --- | --- |
| `sources.run` | `RunSource` | `name` / `description`，另有 `missingProgram` 报错 |
| `sources.bing` | `BingSearchSource` | `search.{name,description}` 与 `suggestion` |
| `sources.calc` | `CalcSource` | `result.{description,action}`、`detail.{input,output}`、`timeout.{name,description}`、`invalidExpression`、`desmos.{name,description}` |
| `sources.everything` | `EverythingSource` | `unavailable.{name,description}`、`busy.*`、`unsupported.*`、`open.{file,folder,drive}` |
| `sources.envProgram` | `EnvProgramSource` | `name` / `description` |
| `sources.installedApplication` | `InstalledApplicationSource` | `name` |
| `sources.welcome` | `WelcomeSource` | `changeConfig.{name,description}`、`repo.*`、`official.*`、`backgroundUnavailable` |

## 4. 占位符与转义

- `{0}`、`{1}` 是 `string.Format` 的占位符，参数顺序即下标顺序；`Localization.Format` 找不到键时原样返回键路径，不会因为缺键抛异常。
- 文案里需要真正的花括号时写成 `{{` 和 `}}`，例如 `ai.prompt.hintFilter` 里的 JSON 示例 `{{"hashes":[...]}}` 格式化后会变成 `{"hashes":[...]}`。
- 所有语言的占位符集合必须与 `zh_CN.json` 一致（例如都含有 `{0}`），否则单测失败 —— 翻译时最容易漏的就是这一条。

## 5. 改动文案的流程

1. 在 `lang/zh_CN.json` 里找到对应领域的分组；没有就按第 2 节的规则新建一个。
2. 改中文，再同步其它语言（暂缺会回退到中文，但发布前最好补齐）。
3. 代码里用 `Localization.Get(...)` / `Localization.Format(...)`，XAML 里用 `{loc:Loc 键}`。
4. 删掉不再使用的键（别再留着旧键）。
5. 跑 `dotnet test`：布局看门狗与语言文件一致性会兜住手滑。

## 6. 单测兜住了什么

`src/CommandPark.Tests/Strings/`：

| 测试 | 覆盖 |
| --- | --- |
| `LocalizationKeyLayoutTest` | 引用与定义**双向一致**（拼错的键、没人用的键都会失败）；深度 ≤ 4；每段 ≤ 2 词；分组宽度上限 |
| `StringCollectionBuilderTest.ShippedLanguageFiles_*` | 每个语言文件的键集合与占位符集合都与 `zh_CN` 一致；切换语言真的能取到译文 |
| `StringCollectionTest`、`MultiStringCollectionTest`、`LanguageConfigTest`、`StringCollectionBuilderTest` | 取值、回退链、缓存、语言标记解析、配置读取 |

其中布局看门狗依赖仓库结构（要能找到 `CommandPark.slnx`），所以它只在仓库里跑，不在发布产物里跑。
